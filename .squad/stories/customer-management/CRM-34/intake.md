## Source — work item (from tracker)

**Title:** CUS-006 Interaction History  
**Type:** Task  
**Status:** In Progress

### Description

User Story

As a support agent, I want to view a customer's interaction history so that I can understand previous customer communications and support activity.

Objective

Display a chronological history of important customer interactions from the CRM.

Scope

This MVP story covers:

	Interaction history on the customer profile

	Chronological timeline

	Interaction type

	Date/time

	Summary/details

	Related ticket where available

	Basic pagination or recent-history display

The implementation should use existing CRM activity data where possible.

UI Requirements

Add an Interactions section/tab to the customer profile.

Example:

Customer Profile

[Overview] [Tickets] [Interactions] [Notes] [Attachments]

Interactions
────────────────────────────────────────────────────

Today · 10:32
🎫 Ticket Created
Ticket #1001
Login problem

Today · 10:45
💬 Customer Message
"I still cannot access my account."

Today · 11:02
👤 Agent Reply
"Please try resetting your password."

Yesterday · 15:20
📧 Email
Previous support communication

Each interaction should display:

	Date/time

	Interaction type

	Short description

	Related ticket when available

	User/agent responsible when available

Newest interactions should appear first.

Interaction Types

For the MVP, support the interaction types required by existing implemented functionality, such as:

	Ticket created

	Customer message

	Agent reply

	Status change

	Assignment

	Internal note

	Email

	WhatsApp

	Live chat

	SMS

	Web form

Not every channel needs a real external integration for this story.

If a channel is not yet integrated, it may appear as seeded/demo interaction data.

API

Get Customer Interactions

{{GET /api/customers/

{id}
/interactions}}

Recommended query parameters:

?page=1
&pageSize=20

Example response:

{
  "items": [
    {
      "id": "interaction-id",
      "type": "CustomerMessage",
      "summary": "Customer reported a login problem.",
      "occurredAt": "2026-08-24T10:45:00Z",
      "actorName": "Ahmed Ali",
      "ticketId": "ticket-id"
    }
  ],
  "page": 1,
  "pageSize": 20,
  "totalCount": 1
}

The final response model should follow the approved domain model.

Backend Requirements

The backend must:

	Require authentication.

	Validate the customer identifier.

	Verify the current user can access the customer.

	Retrieve the customer's interactions.

	Order interactions by date/time descending.

	Support pagination where required.

	Return only authorized information.

	Handle missing customers.

	Handle database failures safely.

Data Requirements

The implementation should reuse existing history/activity records where possible.

Do not create duplicate interaction records for the same business event.

If the existing system does not yet have a suitable interaction/history model, introduce the smallest model necessary for the MVP.

A possible model is:

CustomerInteraction

Id
CustomerId
Type
Summary
OccurredAt
ActorId
TicketId
CreatedAt

The exact model must be aligned with the final domain design.

Integration With Other Features

Customer interactions should be generated by relevant CRM actions where practical.

Examples:

Create Ticket
      ↓
Customer Interaction

Customer Reply
      ↓
Customer Interaction

Agent Reply
      ↓
Customer Interaction

Ticket Assignment
      ↓
Customer Interaction

Status Change
      ↓
Customer Interaction

Do not implement a complex event system for the MVP.

Simple service-level recording is sufficient.

Authorization

Use the authorization model defined in AUTH-003.

At minimum:

	Admin: allowed

	Manager: allowed

	Agent: allowed according to customer access rules

	Customer: only their own interaction/history through the customer portal

A customer must not access another customer's interaction history.

Loading State

Display a loading/skeleton state while interactions are being retrieved.

Empty State

If the customer has no interactions:

No interactions yet.

Customer activity will appear here as support activity occurs.

Do not treat an empty history as an error.

Error State

If the API fails:

Unable to load interaction history.

[Retry]

Do not expose technical exception details.

Validation

Validate:

	Customer ID

	Pagination parameters

Backend validation is authoritative.

Testing

Backend/API Tests

Test:

	Authorized user can retrieve interactions.

	Customer not found.

	Invalid customer ID.

	Unauthenticated request.

	Unauthorized customer access.

	Interactions are returned newest first.

	Pagination works.

	Empty history returns a valid empty response.

	Database failure is handled safely.

Frontend Tests

Test:

	Interactions section renders.

	Interaction timeline displays.

	Loading state appears.

	Empty state appears.

	Error state appears.

	Retry works.

	Related ticket can be opened where implemented.

	Pagination works if implemented.

Manual Verification

	Open a customer profile.

	Open Interactions.

	Verify existing activity is displayed.

	Create a ticket.

	Verify the ticket activity appears.

	Change ticket status.

	Verify the activity appears if implemented.

	Add a customer/agent message.

	Verify the interaction appears.

Edge Cases

Handle:

	Customer has no interactions.

	Customer has many interactions.

	Interaction has no ticket.

	Interaction has no actor.

	Missing interaction details.

	Invalid customer ID.

	Unauthorized access.

	Database/API failure.

	Multiple interactions with the same timestamp.

AI Implementation Instructions

Before implementation:

	Read SDD-001, SDD-002, and SDD-003.

	Read AUTH-003.

	Read CUS-005.

	Inspect existing ticket/history models before creating new models.

	Reuse existing ticket history/activity data where possible.

	Avoid duplicate interaction storage.

	Do not introduce an event bus or complex event architecture.

	Use PostgreSQL and EF Core.

	Keep the implementation simple for the MVP.

	Add backend and frontend tests.

	Run relevant tests.

	Review the implementation against the acceptance criteria.

	Do not implement external communication integrations in this story.

Acceptance Criteria

	Authorized users can view customer interaction history.

	Interactions are displayed chronologically.

	Interaction type is displayed.

	Date/time is displayed.

	Interaction summary/details are displayed.

	Related ticket is displayed where available.

	Loading state is implemented.

	Empty state is implemented.

	Error state is implemented.

	Customer access authorization is enforced.

	Customer data isolation is maintained.

	Pagination works if required by the implementation.

	Relevant backend tests pass.

	Relevant frontend tests pass.

	AI-generated code has been reviewed.

	Implementation follows the SDD.

Definition of Done

	Customer interaction UI implemented.

	Interaction API implemented/reused.

	Interaction data persisted/retrieved through PostgreSQL.

	Authorization implemented.

	Loading/empty/error states implemented.

	Relevant CRM actions create/display interactions where applicable.

	Tests pass.

	Manual verification completed.

	No unnecessary event infrastructure introduced.

	AI-generated code reviewed.

	Acceptance criteria verified.
